# Week 14 — Capstone Harden: API Threat Modeling, the OWASP API Security Top 10 in .NET 9, Deliberate MediatR and AutoMapper, and a Local Grafana + Loki + Tempo Observability Stack

Welcome to **C9 · Crunch Sharp**, Week 14 — the **capstone harden** week. Last week you stood up the integration baseline: all three clients of the **Polyglot Workshop** (the ASP.NET Core 9 backend, the .NET MAUI mobile client, and the Blazor admin) compiled against the one shared `.proto` contract, and your integration suite ran green in CI against ephemeral PostgreSQL and Keycloak containers via Testcontainers. The system *works*. This week the question changes from "does it work" to "can I trust it, and can I operate it." The theme is one sentence, and it is the lecture title: **hardening is editing**. By the end of the week your diff is, on net, smaller — you will delete a hand-rolled mapper, collapse three near-identical endpoint handlers into one MediatR pipeline, remove a `[AllowAnonymous]` that should never have shipped, and replace a `Console.WriteLine` debugging habit with a trace you can follow from the API edge through the gRPC service into PostgreSQL and back out — all while *adding* the integration tests that prove the auth surface is closed.

The first thing to internalize is that **hardening is a property of the boundary, not of the code behind it**. The Polyglot Workshop has exactly three boundaries that an attacker can reach: the Minimal API surface over HTTP, the gRPC service over HTTP/2, and the SignalR hub over the WebSocket upgrade. Everything else — the EF Core `DbContext`, the Dapper analytics queries, the background outbox worker — is reachable *only* through one of those three doors. Threat modeling is the disciplined enumeration of what an attacker can send through each door, what they can learn from the response, and what they can make the system do that it should not. We do this with a lightweight, repeatable method (STRIDE per boundary, written down in a `THREATMODEL.md` that lives in the repo), not with a security consultant and a six-week engagement. The canonical reference for the method is the OWASP Threat Modeling cheat sheet at <https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html>, and the canonical catalog of what actually goes wrong at an API boundary is the **OWASP API Security Top 10 (2023)** at <https://owasp.org/API-Security/editions/2023/en/0x11-t10/>. Read both before Lecture 1.

The second thing to internalize is that the OWASP API Top 10 is, for a .NET engineer, **mostly a list of authorization bugs**. Look at the 2023 list: API1 Broken Object Level Authorization (BOLA), API2 Broken Authentication, API3 Broken Object Property Level Authorization, API5 Broken Function Level Authorization. Four of the top five are "the caller asked for something they should not have been allowed to have, and you gave it to them." In ASP.NET Core the antidote is **resource-based authorization** (`IAuthorizationService.AuthorizeAsync(user, resource, policy)`), which you met in Week 7's `RequireOwner` policy, applied *consistently* — at the boundary, before the handler touches the database, for every object the caller names by id. The single most common BOLA in a workshop platform is `GET /lessons/{id}/submissions/{submissionId}` returning a submission that belongs to a *different learner* because the handler filtered by `submissionId` but never checked that the submission's `LearnerId` matches the caller. Lecture 1 walks the workshop's full object graph and marks every endpoint that names an object by id — those are your BOLA candidates, and every one of them gets an integration test this week. Citation: <https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/>.

The third thing to internalize is **MediatR is a tool for cross-cutting concerns, not a religion**. The reflexive misuse of MediatR is to wrap every handler in a `record FooCommand : IRequest<FooResult>` and a `FooCommandHandler`, doubling the file count and adding an indirection that buys nothing. The deliberate use of MediatR is to introduce it **exactly when you have a cross-cutting concern that you would otherwise copy-paste into every handler** — validation, authorization, logging, transaction scoping, outbox enqueueing. Those become `IPipelineBehavior<TRequest, TResponse>` implementations that run once, in order, for every request that flows through the mediator, and the per-feature handler shrinks to the business logic alone. For the Polyglot Workshop the earning-its-keep case is precise: a `ValidationBehavior` (FluentValidation), an `AuthorizationBehavior` (resource-based checks expressed as `IAuthorizationRequirement`s on the request), and a `TransactionBehavior` (open a transaction, run the handler, enqueue the outbox row, commit). MediatR is worth its weight the moment you have those three behaviors; before that, it is ceremony. Lecture 2 makes the decision rule explicit and shows the before/after diff — which, true to the theme, *removes* lines. Citation: <https://github.com/jbogard/MediatR/wiki/Behaviors>.

The fourth thing to internalize is that **AutoMapper is for mechanical, name-matched DTO projection — and nothing else**. The honest case for AutoMapper is the boring one: you have an EF Core entity `Submission { Id, LearnerId, LessonId, Content, Grade, SubmittedAtUtc, ... }` and a `SubmissionDto { Id, LessonId, Grade, SubmittedAtUtc }` whose properties are a name-matched subset, and you do not want to hand-write `new SubmissionDto { Id = s.Id, LessonId = s.LessonId, ... }` in fifteen places. AutoMapper's `ProjectTo<SubmissionDto>(query)` even pushes the projection into the SQL `SELECT` so you never materialize the columns you drop. The dishonest case — the one we *delete* this week — is using AutoMapper for anything with logic: conditional mapping, flattening that needs a join the profile cannot express, security-sensitive field stripping, or any mapping where a reviewer cannot tell from the DTO shape what the output will be. Those map to a hand-written, testable, greppable mapping method. The rule: **AutoMapper where the mapping is obvious from the names, a hand-written method where it is not.** Lecture 2 closes with the `ProjectTo` pattern and the list of three mappings in the workshop that AutoMapper should *not* touch. Citation: <https://docs.automapper.org/en/stable/Queryable-Extensions.html>.

The fifth thing to internalize is the **three signals of observability and what each one is for**. Logs are discrete events with structure (`Serilog` writes them as JSON with named properties, not interpolated strings). Metrics are aggregatable numbers over time (request rate, error rate, p99 latency — the RED method — emitted via `System.Diagnostics.Metrics` and scraped by Prometheus or pushed via OTLP). Traces are causally-linked spans that follow one request across process boundaries (the API span, the gRPC span, the EF Core command span, all sharing one `TraceId`, emitted via `System.Diagnostics.ActivitySource` and exported over OTLP). The mistake is to reach for the wrong one: people grep logs to compute a p99 (use a metric), or stare at a metrics dashboard to understand why *one specific request* failed (use a trace). This week you wire all three from the .NET 9 OpenTelemetry SDK to a **local Grafana + Loki + Tempo** stack via `docker compose`: **Loki** stores the structured logs, **Tempo** stores the traces, **Prometheus** scrapes the metrics, and **Grafana** is the single pane of glass that correlates them — click a slow span in Tempo, jump to the logs for that `TraceId` in Loki, see the metric that alarmed in Prometheus. The connective tissue is the **exemplar**: a metric data point that carries the `TraceId` of an exemplary request, so a spike on the latency graph links directly to a trace. Lecture 3 builds the whole stack and the `otel-collector` config. Citation: <https://opentelemetry.io/docs/languages/net/> and <https://grafana.com/docs/tempo/latest/>.

The sixth thing to internalize is that **auth is not done until it is covered by integration tests**. A unit test that asserts `AuthorizationHandler` returns `Failed` for the wrong user is necessary but not sufficient — it does not prove that the *endpoint* is wired to the handler, that the policy name is spelled correctly in the `[Authorize(Policy = "...")]` attribute, or that an anonymous request to the gRPC method is actually rejected with `Unauthenticated`. The proof is an integration test: `WebApplicationFactory<Program>` with a Testcontainers Keycloak that mints a real token for "learner alice," another for "learner bob," and a third for "instructor carol," then asserts that alice cannot read bob's submission (BOLA), that an anonymous caller gets 401 on every authenticated endpoint, and that a learner gets 403 on every instructor-only function (BFLA). This week's capstone milestone is, in one line: **every authenticated boundary has an integration test that proves both the allow and the deny path, and the THREATMODEL.md maps every test back to the OWASP item it covers.** Lecture 1 and Exercise 1 build the auth test harness; the mini-project is the milestone itself. Citation: <https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests>.

By the end of this week you will be the engineer who, handed a production incident, opens Grafana instead of SSH — who reads the trace, finds the slow span, jumps to its logs by `TraceId`, and names the cause from the dashboard alone; and who, handed a new endpoint in code review, asks "where is the resource-based authorization check and where is the integration test that proves the deny path" before asking anything else.

## Learning objectives

By the end of this week, you will be able to:

- **Threat-model** the three boundaries of the Polyglot Workshop (Minimal API over HTTP, gRPC over HTTP/2, SignalR over the WebSocket upgrade) with STRIDE-per-boundary, and write the result into a repo-resident `THREATMODEL.md`. Cite the OWASP Threat Modeling cheat sheet at <https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html>.
- **Enumerate** the OWASP API Security Top 10 (2023) and map each item to a concrete .NET mitigation: BOLA → resource-based authorization, Broken Authentication → token validation hardening, BOPLA → DTO allow-lists, BFLA → policy-gated functions, Unrestricted Resource Consumption → rate limiting and pagination caps. Cite <https://owasp.org/API-Security/editions/2023/en/0x11-t10/>.
- **Implement** resource-based authorization with `IAuthorizationService.AuthorizeAsync(user, resource, requirement)` and an `AuthorizationHandler<TRequirement, TResource>`, applied at the API edge before the handler reads the database. Cite <https://learn.microsoft.com/en-us/aspnet/core/security/authorization/resourcebased>.
- **Cover** the auth surface with integration tests using `WebApplicationFactory<Program>` and a Testcontainers Keycloak, asserting both the allow path and the deny path (401 anonymous, 403 wrong-role, 403/404 cross-tenant BOLA) for every authenticated boundary. Cite <https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests> and <https://dotnet.testcontainers.org/>.
- **Introduce** MediatR deliberately, as `IPipelineBehavior<TRequest, TResponse>` implementations for validation, authorization, and transaction/outbox scoping — and articulate the decision rule for when a feature does *not* warrant a request/handler pair. Cite <https://github.com/jbogard/MediatR/wiki/Behaviors>.
- **Apply** AutoMapper only to name-matched, logic-free DTO projection via `ProjectTo<TDto>(query)`, and hand-write the mappings that carry logic or strip security-sensitive fields. Justify each choice. Cite <https://docs.automapper.org/en/stable/Queryable-Extensions.html>.
- **Instrument** the backend with the .NET 9 OpenTelemetry SDK: `ActivitySource` spans, `Meter`-based RED metrics, and Serilog structured logs, all exported over OTLP. Cite <https://opentelemetry.io/docs/languages/net/> and <https://learn.microsoft.com/en-us/dotnet/core/diagnostics/observability-with-otel>.
- **Stand up** a local Grafana + Loki + Tempo + Prometheus stack via `docker compose`, wire an OpenTelemetry Collector, and correlate a single request across all three signals — click a slow trace in Tempo, pivot to its logs in Loki by `TraceId`, read the metric in Prometheus. Cite <https://grafana.com/docs/tempo/latest/> and <https://grafana.com/docs/loki/latest/>.
- **Emit and read exemplars** — metric data points tagged with a `TraceId` — so a latency spike on a Grafana panel links directly to the trace that caused it. Cite <https://opentelemetry.io/docs/specs/otel/metrics/data-model/#exemplars>.
- **Rate-limit** the API surface with the built-in `Microsoft.AspNetCore.RateLimiting` middleware (fixed-window, sliding-window, token-bucket, concurrency) to close OWASP API4 Unrestricted Resource Consumption. Cite <https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit>.
- **Cite** the OWASP API Security Top 10, the OWASP cheat sheets, Microsoft Learn security and observability documentation, the OpenTelemetry .NET docs, and the Grafana stack documentation for every technique covered.

## Topics covered

- **Threat modeling, lightweight.** STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) applied per boundary; the data-flow diagram; the trust boundary; writing it down in `THREATMODEL.md` so it is reviewable and reviewed.
- **The OWASP API Security Top 10 (2023).** API1 BOLA, API2 Broken Authentication, API3 BOPLA, API4 Unrestricted Resource Consumption, API5 BFLA, API6 Unrestricted Access to Sensitive Business Flows, API7 SSRF, API8 Security Misconfiguration, API9 Improper Inventory Management, API10 Unsafe Consumption of APIs — each mapped to a .NET mitigation.
- **Resource-based authorization.** `IAuthorizationService.AuthorizeAsync`, `AuthorizationHandler<TRequirement, TResource>`, `IAuthorizationRequirement`, the "check before you read" discipline, the difference between 403 and 404 for resources you must not even confirm exist.
- **Tenant-aware authorization.** The workshop is multi-tenant (one org's instructors cannot see another org's lessons); the tenant claim, the `TenantRequirement`, and the EF Core global query filter that enforces it in defense-in-depth.
- **Authentication hardening.** Token-validation parameters audited (`ValidateIssuer`, `ValidateAudience`, `ValidateLifetime`, clock skew), the Keycloak realm and audience, the gRPC `Unauthenticated` vs `PermissionDenied` status codes, the SignalR `access_token` query-string carve-out reviewed for leakage.
- **Auth integration testing.** `WebApplicationFactory<Program>` with a real Testcontainers Keycloak, minting tokens for distinct principals, asserting allow and deny paths, the test-per-OWASP-item mapping.
- **MediatR, deliberately.** `IRequest<T>` / `IRequestHandler<T>`, `IPipelineBehavior<TRequest, TResponse>`, ordering of behaviors, the `ValidationBehavior` / `AuthorizationBehavior` / `TransactionBehavior` triad, the decision rule for *not* using MediatR.
- **FluentValidation as a pipeline behavior.** `AbstractValidator<T>`, the `ValidationBehavior` that runs every registered validator and throws a `ValidationException` translated to RFC 9457 ProblemDetails.
- **AutoMapper, deliberately.** `Profile`, `ProjectTo<TDto>` pushing projection into SQL, `AssertConfigurationIsValid()` in a test, and the three workshop mappings that AutoMapper must *not* own.
- **Serilog structured logging.** JSON sink, the `TraceId`/`SpanId` enrichers, log levels by environment, the rule that log messages are templates with named properties, never interpolated strings.
- **OpenTelemetry in .NET 9.** `ActivitySource` and manual spans, automatic instrumentation for ASP.NET Core / gRPC / EF Core / Npgsql / HttpClient, `Meter` and the RED metrics, the OTLP exporter, the resource attributes (`service.name`, `service.version`).
- **The Grafana + Loki + Tempo stack.** `docker compose` topology, the OpenTelemetry Collector pipeline (receivers → processors → exporters), Loki for logs, Tempo for traces, Prometheus for metrics, Grafana datasources and the trace-to-logs correlation.
- **Exemplars.** Metric points carrying a `TraceId`; the Prometheus `--enable-feature=exemplar-storage` flag; the Grafana panel that links a latency spike to a trace.
- **Rate limiting.** `Microsoft.AspNetCore.RateLimiting`, the four algorithms (fixed window, sliding window, token bucket, concurrency), partitioning by tenant or by authenticated user, the `429` response with `Retry-After`.
- **The worked milestone: the hardened Polyglot Workshop.** Auth fully integration-tested, MediatR pipeline behaviors in place, AutoMapper scoped to projection, all three signals flowing to Grafana, a `THREATMODEL.md` and the deny-path tests it indexes.

## The capstone-milestone promise

C9 treats `dotnet build` as a contract: **`Build succeeded · 0 warnings · 0 errors`**. For the capstone weeks we add a second contract, the **milestone gate**. Week 13's gate was "the integration baseline is green." Week 14's gate is **production polish**, and it is binary — each item is done or it is not:

1. **Every authenticated boundary has an integration test that proves both the allow and the deny path.** Anonymous → 401. Wrong role → 403. Cross-tenant / cross-owner object access → 403 or 404 (never the object). The tests run against a real Testcontainers Keycloak, not a fake.
2. **`THREATMODEL.md` exists, enumerates the three boundaries with STRIDE, and indexes every deny-path test back to the OWASP API Top 10 item it covers.** A boundary without a row is a boundary nobody threat-modeled.
3. **MediatR is present only as pipeline behaviors that earn their keep** (validation, authorization, transaction/outbox) — and the harden diff *removes* more handler boilerplate than it adds.
4. **AutoMapper is scoped to name-matched projection** (`ProjectTo`), `AssertConfigurationIsValid()` passes in a test, and the three logic-bearing mappings are hand-written and unit-tested.
5. **All three signals flow to the local Grafana + Loki + Tempo stack**, and you can demonstrate the correlated-incident walkthrough: a slow trace in Tempo → its logs in Loki by `TraceId` → the metric that alarmed in Prometheus.

A pull request that adds an endpoint naming an object by id, without a resource-based authorization check and a deny-path integration test, is — by definition — a pull request that has not been reviewed. The theme restated: **hardening is editing.** If your week-14 diff is bigger than your week-13 diff, you have probably added features instead of hardening the ones you have.

> **Note on packages.** MediatR (`MediatR` 12.x), AutoMapper (`AutoMapper` 13.x + `AutoMapper.Extensions.Microsoft.DependencyInjection`), FluentValidation (`FluentValidation` 11.x + `.AspNetCore` + `.DependencyInjectionExtensions`), Serilog (`Serilog.AspNetCore`, `Serilog.Sinks.OpenTelemetry`), and the OpenTelemetry SDK (`OpenTelemetry.Extensions.Hosting`, `OpenTelemetry.Instrumentation.AspNetCore`, `.GrpcNetClient`, `.EntityFrameworkCore`, `OpenTelemetry.Exporter.OpenTelemetryProtocol`). Rate limiting is in-box (`Microsoft.AspNetCore.RateLimiting`, part of the ASP.NET Core 9 shared framework). All free, all open source. The Grafana / Loki / Tempo / Prometheus stack runs from public Docker images. No paid tooling is required.

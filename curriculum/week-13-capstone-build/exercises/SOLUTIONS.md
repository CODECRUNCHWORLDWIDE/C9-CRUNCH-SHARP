# Week 13 Exercise Solutions

These are the worked solutions to the four exercises. Each solution shows the canonical implementation, the verification output the grader looks for, and the most common ways the exercise gets done wrong. Read your own solution first; check it against the canonical one second. The point of this file is not to be copied — the point is to surface the patterns and the failure modes so you recognize them when they show up in your own capstone code over the next three weeks.

The four exercises build the same vertical slice the lectures build, in order: (1) author the contract and prove generation, (2) scaffold the service and the migration, (3) implement the enroll slice end to end, (4) lock it in with the integration baseline. Do them in order; each depends on the last.

## Exercise 01 — Author the contract and prove generation

The canonical solution is the `workshop.proto` from Lecture 1 and the `Workshop.Contracts.csproj` that compiles it. The single thing this exercise is testing is whether you can make the *generated* type appear — so the verification is a one-line program that names a generated type and compiles.

```csharp
// Program.cs in a throwaway console project that references Workshop.Contracts
using Workshop.Contracts.V1;

var req = new EnrollRequest { LessonId = Guid.NewGuid().ToString() };
Console.WriteLine($"Generated type compiled: {req.GetType().FullName}");
```

### Verification output

```
$ dotnet build Workshop.Contracts
  Workshop.Contracts -> .../bin/Debug/net9.0/Workshop.Contracts.dll
Build succeeded · 0 warnings · 0 errors

$ dotnet run --project ProveGeneration
Generated type compiled: Workshop.Contracts.V1.EnrollRequest
```

If `EnrollRequest` does not resolve, the generation did not happen. Confirm in order: the `<Protobuf Include=...>` item points at the real path; `Grpc.Tools` is referenced; you actually built (generation runs at build, not at edit). Inspect `obj/Debug/net9.0/Protos/Workshop.cs` — if it is absent, `protoc` did not run.

### Where the generated code lands

The build emits two files under `obj/Debug/net9.0/Protos/` (the path varies with configuration and TFM). Inspect them — not to copy, but to understand what you bought:

```
obj/Debug/net9.0/Protos/
  Workshop.cs        <-- the message types: Lesson, Enrollment, EnrollRequest, ...
                         each an immutable-ish C# class implementing IMessage<T>
  WorkshopGrpc.cs    <-- the service: Workshop.WorkshopBase (server) +
                         Workshop.WorkshopClient (client), one method pair per RPC
```

If only `Workshop.cs` appears and `WorkshopGrpc.cs` is absent, `GrpcServices` is set to `Messages` (or omitted on a path that defaults to messages-only) rather than `Both` — the messages generated but the service did not. That is the most common "it built but the client type does not exist" cause.

### Common stumbles

- **Wrong `csharp_namespace`.** The proto's `option csharp_namespace = "Workshop.Contracts.V1";` controls the generated namespace. If you omit it, the namespace is derived from `package workshop.v1` as `Workshop.V1`, and every `using Workshop.Contracts.V1;` fails. Pick one and be consistent across the repo.
- **`Grpc.Tools` without `PrivateAssets`.** Leaving off `<PrivateAssets>All</PrivateAssets>` makes the build-time tool flow transitively to every consumer as a runtime dependency. It still compiles, but it pollutes the dependency graph. Fix it now while there is one `.csproj`.
- **Checking generated files into git.** `Workshop.cs` and `WorkshopGrpc.cs` live in `obj/` and regenerate on every build. Add `obj/` and `bin/` to `.gitignore`; never commit generated code.
- **Missing the well-known-types import.** Using `google.protobuf.Timestamp` without `import "google/protobuf/timestamp.proto";` and a `ProtoRoot` that resolves it gives `File not found`. The `Google.Protobuf` package ships the well-known `.proto` files; `Grpc.Tools` finds them automatically, but only if the import line is present.
- **Editing the generated `.cs` to "fix" something.** The files carry a `// <auto-generated>` header for a reason — your edit vanishes on the next build. If a generated property is wrong, the `.proto` is wrong; fix the source.

### Common stumbles

- **Forgetting `public partial class Program { }`.** Without it, Exercise 4's `WebApplicationFactory<Program>` will not compile (`Program is inaccessible due to its protection level`). Add the line at the bottom of `Program.cs` now, even though the tests come later — the lecture flags this for exactly this reason.
- **`AddDbContext` instead of `AddDbContextPool`.** Both work; the pooled form is the capstone default for the same throughput reason as Week 12. Not a correctness bug, but the grader expects the pooled form.
- **No `dotnet-ef` on the path, or the wrong version.** `dotnet ef --version` must print `9.0.x`. A `dotnet-ef` 8.x against an EF Core 9 project produces confusing design-time errors. Reinstall with `--version 9.0.0`.
- **Entities that *are* the contract messages.** A frequent shortcut is to put `[ProtoContract]`-style attributes on, or even persist, the generated `Lesson` message directly. Do not. The generated types are immutable-ish wire shapes with `int` enums and string GUIDs; the entities are persistence shapes with `Guid`, `DateTimeOffset`, and navigation properties. Keep them separate and map at the boundary.

### The model configuration that produces the right SQL

The snake_case tables, the unique index, and the cascade do not happen by accident — they are `OnModelCreating` configuration. The canonical form:

```csharp
protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Lesson>(e =>
    {
        e.ToTable("lessons");
        e.HasKey(l => l.Id);
        e.Property(l => l.Title).HasMaxLength(200).IsRequired();
        e.Property(l => l.CreatedAt);                 // maps to timestamptz under Npgsql
        e.HasMany(l => l.Enrollments)
         .WithOne(en => en.Lesson)
         .HasForeignKey(en => en.LessonId)
         .OnDelete(DeleteBehavior.Cascade);           // CREATE ... ON DELETE CASCADE
    });

    b.Entity<Enrollment>(e =>
    {
        e.ToTable("enrollments");
        e.HasKey(en => en.Id);
        e.HasIndex(en => new { en.LessonId, en.LearnerId })
         .IsUnique();                                 // "a learner enrolls once"
    });
}
```

The composite `HasIndex(...).IsUnique()` is the line that turns the business rule "a learner enrolls in a lesson at most once" into a database constraint. It is what makes the idempotency branch in Exercise 3 a *backstop* (the DB rejects a duplicate even under a race), with the read-first check the *primary* path. Citation: <https://learn.microsoft.com/en-us/ef/core/modeling/indexes>.

## Exercise 03 — The enroll slice end to end

The canonical solution is the `Enroll` override from Lecture 2: validate the `lesson_id`, resolve the stub learner, confirm the lesson exists, short-circuit on an existing enrollment (idempotency), persist, map back via `ToContract`. The slice is small; the *discipline* is the lesson. The method reads as a numbered sequence, and the order is load-bearing:

```csharp
public override async Task<Enrollment> Enroll(EnrollRequest request, ServerCallContext context)
{
    // 1. Validate the input before touching the database.
    if (!Guid.TryParse(request.LessonId, out var lessonId))
        throw new RpcException(new Status(StatusCode.InvalidArgument, "lesson_id must be a GUID"));

    // 2. Resolve the learner (a header stub this week; a JWT claim in Week 14).
    var learnerId = ResolveLearnerId(context);

    // 3. Confirm the lesson exists — the invariant that yields NotFound.
    var exists = await _db.Lessons.AnyAsync(l => l.Id == lessonId, context.CancellationToken);
    if (!exists)
        throw new RpcException(new Status(StatusCode.NotFound, "lesson not found"));

    // 4. Read-first idempotency: return the existing enrollment if there is one.
    var existing = await _db.Enrollments
        .FirstOrDefaultAsync(e => e.LessonId == lessonId && e.LearnerId == learnerId,
            context.CancellationToken);
    if (existing is not null)
        return ToContract(existing);

    // 5. Persist the new enrollment; the unique index is the race backstop.
    var entity = new Enrollment
    {
        Id = Guid.NewGuid(), LessonId = lessonId, LearnerId = learnerId,
        EnrolledAt = DateTimeOffset.UtcNow,
    };
    _db.Enrollments.Add(entity);
    await _db.SaveChangesAsync(context.CancellationToken);

    _logger.LogInformation("Learner {LearnerId} enrolled in lesson {LessonId}", learnerId, lessonId);
    return ToContract(entity);
}
```

### Common stumbles

- **Mapping inline instead of in `ToContract`.** Spreading the entity→contract conversion across the method (a `new Enrollment { ... }` here, another there) is how the two shapes silently drift. One conversion method, one place.
- **`Timestamp.FromDateTime` instead of `FromDateTimeOffset` with a non-UTC `DateTime`.** `google.protobuf.Timestamp` requires UTC. `Timestamp.FromDateTime(DateTime.Now)` throws `Timestamp value must be in UTC`. Store and convert `DateTimeOffset` in UTC; the lecture uses `DateTimeOffset.UtcNow`.
- **Relying on a try/catch of the unique-index violation for idempotency.** It "works" but turns an expected case into an exception and a failed transaction. The canonical solution *reads first* (step 4) and only inserts if absent. The unique index is the backstop against a race, not the primary idempotency mechanism.
- **Throwing a bare `Exception` instead of `RpcException`.** A gRPC method must surface failures as an `RpcException` with a `StatusCode` so the client sees `NotFound`/`InvalidArgument`, not a generic `Internal`. Cite <https://learn.microsoft.com/en-us/aspnet/core/grpc/error-handling>.

## Exercise 04 — The integration baseline

The canonical solution is the `WorkshopFactory` + `EnrollSliceTests` from Lecture 3: a `PostgreSqlContainer` started in `InitializeAsync`, the connection string redirected via `ConfigureWebHost`, a generated `WorkshopClient` over `Server.CreateHandler()`, and the three tests (happy / `NotFound` / idempotent).

### Common stumbles

- **Using SQLite-in-memory "to be fast."** It hides the bugs the baseline exists to catch: `timestamptz` round-tripping, the unique-index violation shape, snake_case case folding. The capstone's rule is a *real* PostgreSQL via Testcontainers, every time. Cite <https://dotnet.testcontainers.org/modules/postgres/>.
- **A real `GrpcChannel.ForAddress("https://localhost:7080")` in the test.** That tries to open a real socket to a server that is not running. Use `Server.CreateHandler()` from the factory so the call routes into the in-memory `TestServer`. Cite <https://learn.microsoft.com/en-us/aspnet/core/grpc/test-services>.
- **Forgetting `IAsyncLifetime`.** If the container is built but never `StartAsync`'d, the connection string points at nothing and the first query hangs or refuses. The `InitializeAsync`/`DisposeAsync` pair (from `IAsyncLifetime`) is what starts and stops it around the class.
- **Order-dependent tests sharing one learner id.** If two tests enroll the *same* learner in the *same* lesson, the idempotency branch makes the second a no-op and an assertion that expected a fresh row fails. Give each test a distinct learner id (or lesson id) so they are independent. Cite the xUnit shared-context docs at <https://xunit.net/docs/shared-context>.
- **Green locally, red in CI because Docker is missing on a self-hosted runner.** `ubuntu-latest` has Docker; a self-hosted runner may not. Symptom: `Cannot connect to the Docker daemon at unix:///var/run/docker.sock`. This is the exact failure Challenge 2 makes you diagnose. Cite <https://docs.github.com/en/actions/use-cases-and-examples/building-and-testing/building-and-testing-net>.

## A closing note on the four together

The four exercises are not four topics — they are one slice, built four times deeper. The contract (1) is meaningless until a service implements it (2); the service is unproven until the slice runs end to end (3); the slice is "works on my machine" until the baseline locks it green in CI (4). When all four are done, you have the *shape* the entire capstone repeats: every RPC you add in Weeks 14–15 is proto field → entity → service method → contract mapping → integration test, green in CI, in that order. Learn the shape once here; reuse it forty times after.

The one place where all four exercises meet is the `ToContract` boundary — the single method that converts a persistence `Enrollment` (with `Guid`, `DateTimeOffset`, navigation properties) into a wire `Enrollment` (with string GUIDs, a `Timestamp`, and no navigations). It is small, it is boring, and it is the seam that keeps the two shapes from drifting:

```csharp
private static Workshop.Contracts.V1.Enrollment ToContract(Data.Enrollment e) => new()
{
    Id = e.Id.ToString(),
    LessonId = e.LessonId.ToString(),
    LearnerId = e.LearnerId.ToString(),
    EnrolledAt = Timestamp.FromDateTimeOffset(e.EnrolledAt.ToUniversalTime()),
};
```

Three things this one method gets right that learners get wrong inline: the GUIDs are `.ToString()`-encoded once, in one place; the `Timestamp` is built from a *UTC* `DateTimeOffset` (the `.ToUniversalTime()` is the guard against the `Timestamp value must be in UTC` throw); and there is exactly one `new Enrollment { ... }` in the whole codebase, so a renamed contract field changes one line, not five. When you add `CreateLesson` you write `ToContract(Lesson)` the same way; when you add `SubmitExercise` you write `ToContract(Submission)`. The boundary is the pattern, repeated.

A final note on *order of operations* across the four: do not be tempted to write the integration test (4) before the slice (3) compiles, or the slice before the migration (2) applies, or the migration before the contract (1) generates. Each exercise's green state is the next one's precondition. The single most common way this week goes sideways is a learner who scaffolds all four projects at once, wires nothing end to end, and spends Saturday debugging four half-built layers at the same time. Finish one, prove it, move on. That sequencing *is* the vertical-slice discipline — it is not a study tip, it is the engineering method the whole capstone is built to teach.

Read the patterns. Reproduce them. Then build the milestone.
